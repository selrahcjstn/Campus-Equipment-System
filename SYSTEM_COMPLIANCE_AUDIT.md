### Concurrency boundary

The isolated SQLite configuration reported `has_select_for_update=False`, `journal_mode=delete`, and `busy_timeout=5000ms`. SQLite does not supply row locks for `SELECT FOR UPDATE`. Safety here combines first conditional/no-op writes acquiring writer serialization, atomic rollback, conditional state updates and partial unique indexes. The views catch busy/integrity errors and report conflict/retry messages. The 30 races produced ValidationError losers, not timeouts. These results do not prove throughput, fairness, every possible interleaving or PostgreSQL/MySQL behavior. The PDF explicitly permits SQLite when its limits are explained.

### Rejection versus cancellation

Only Pending requests can be rejected; Pending has no reservations to release. Approved requests are cancelled to release their reservations. Rejecting an Approved request is deliberately refused, as the PDF workflow requires; it is not a missing reservation-release path.

### Critical violations

No P0 duplicate allocation, double issue, double return, unauthorized state change or partial database save was reproduced. The previously reported review, dashboard and overdue behavior gaps now have implementations and regression coverage. Remaining concerns are the live demo data, historical signing key, legacy import boundaries, and unverified external evidence. Untested penetration/concurrency scenarios remain outside any claim of exhaustive security.
